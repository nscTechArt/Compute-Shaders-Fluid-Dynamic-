# AGENTS.md

## What this is

A Unity compute-shader fluid simulation (GPU Navier–Stokes / stable fluids), structured as a reusable engine plus three demo scenes. Educational repo tied to the author's blog posts (linked in README.md). Data lives in structured buffers manipulated entirely by compute shaders; CPU code only builds/presides over the dispatch pipeline.

- Unity version: **2022.3.62f3** (README still says 2019.1.14f1 — trust ProjectSettings, not the README).
- Built-in (Legacy) render pipeline only. Developed and tested on **Windows / DX11**. Do not migrate to URP/HDRP.

## Building & verifying changes

There is no CLI build, test runner config, lint, or typecheck — this is a plain Unity project:

- Open the project in Unity 2022.3 LTS and press Play on a scene under `Assets/Scenes` to verify.
- The root `.sln` / `Assembly-CSharp.csproj` are generated by Unity for IDE intellisense, are gitignored, and should never be hand-edited or committed.
- There are no asmdefs: all scripts compile into `Assembly-CSharp`, global namespace, no custom `using` namespaces.
- Kernel-level regressions are checked via the manual test scenes (see Testing below).

## Directory map

- `Assets/Scripts/FluidSimulater.cs` — core engine class (pipeline steps: advect, diffuse, project, add dye/force, borders…). Yes, the name is misspelled; it's referenced everywhere — do not rename.
- `Assets/Scripts/FluidGPUResources.cs` — owns all ComputeBuffers/RenderTextures; `Create()`/`Release()` manage lifetime.
- `Assets/Scripts/Utility/ComputeShaderUtility.cs` — static kernel-handle reflection system: `GetKernelHandle`, `CheckGetDispatchDimensions`. Initialized/released by `FluidSimulater.Initialize()`/`Release()`.
- `Assets/Scripts/Simple2DFluidSim.cs`, `Simple2DFluidSimArbitaryBoundary.cs`, `PersianGardenDemoSceneMaster.cs`, `VastLandDemo/*Master.cs` — per-scene masters showing correct engine usage (init → build pipeline → Tick → Release).
- `Assets/Scripts/Tests/` — scene-driven test MonoBehaviours, one per kernel/step.
- `Assets/Shaders/Resources/FluidDynamic/*.compute` — the simulation kernels: `Navier_Stokes.compute` (advection, divergence, gradient subtraction), `Solvers.compute` (Jacobi), `Boundary_Handling.compute`, `UserInput.compute`, `StructuredBufferUtility.compute`, `StructuredbufferToTexture.compute`.
- `Assets/Shaders/Resources/DemoScene|VastLandFogDemo/` — rendering-only shaders.
- `Assets/Scenes/UnitKernelTests/`, `Assets/Scenes/CPUTests/` — one scene per test script.
- `documentation/` — GIFs/screenshots embedded in the README; update paths carefully if moving assets.
- Ignore directories: `Library/`, `Logs/`, `UserSettings/`, `obj/`, `temp/` (generated, gitignored).

## Architecture rules that matter when editing

To add or change a kernel/solver step (from README "Adding New Things"):

1. Write/edit the kernel in the appropriate `.compute` file (solvers belong in `Solvers.compute`).
2. Cache the handle as a `_handle_*` field in `FluidSimulater`, fetched in `Initialize()` via `ComputeShaderUtility.GetKernelHandle(shader, "KernelName")`.
3. Any new buffers go in `FluidGPUResources`: declare field, allocate in `Create()`, free in `Release()`.
4. Static/uniform params set once → in `FluidSimulater.Initialize()`; per-frame values → in `Tick(float)`; per-dispatch params → in the dispatching method itself.
5. Every pipeline function must start with an `IsValid()` guard, and must dispatch through `DispatchComputeOnCommandBuffer(...)` — never raw `Dispatch()`. That call goes through the reflection system, which validates thread-group dimensions against the shader's actual `numthreads`.

Lifecycle contract every entry point depends on: `fluid_simulater.Initialize()` before any use → `resources = new FluidGPUResources(fluid_simulater)` + `resources.Create()` → per-frame work via `Tick()`/pipeline calls → teardown with `resources.Release()` and `fluid_simulater.Release()` (OnDestroy / OnApplicationQuit).

Data layout gotchas: fields are `simulation_dimension × simulation_dimension` structured buffers dispatched as `(dim, dim, 1)` groups; ping-pong during solve uses the **static** `FluidGPUResources.buffer_ping/buffer_pong`; boundary handling relies on cardinal-direction LUT buffers generated by `ArbitaryBoundaryLUTGenerator.cs`.

## Conventions

- Intentional misspellings are baked into names and must be preserved for consistency: `FluidSimulater`, `Arbitary(Boundary)`, `meshe/`, `Visualiuse`, `kernles`. Search by these spellings.
- Code style: `_underscore_prefixed` private fields, snake_case locals, long explanatory comments on nearly every step (maintain this density — comments teach the technique), column-aligned member declarations in some files. Match surrounding style exactly.
- Unity rule: every asset has a `.meta` file; never delete `.meta`s, hand-edit GUIDs, or create assets without letting Unity generate their meta.

## Commit messages

Every commit must follow **`scope: subject`** on a single line — reference format is `init: open project with unity 2022` (22b5f05).

- `scope`: short lowercase noun naming the touched area (`shaders`, `scripts`, `scenes`, `docs`, `init`, …).
- `subject`: concise, starts lowercase, no trailing period.
- Never merge unrelated changes into one commit; split by scope instead. Older commits predate this convention — don't imitate them. A `.gitmessage` template sits at the repo root and is wired into `git config commit.template`.

## Testing

No CI and no automated (NUnit) suite despite the Unity Test Framework package being installed. Tests are interactive scenes: open `Assets/Scenes/UnitKernelTests/Test<Step>.unity` (or `CPUTests/` for CPU-side structures), press Play, and check the console/on-screen output. Run the matching test scene after modifying any kernel or pipeline step.

## Read before touching sensitive areas
